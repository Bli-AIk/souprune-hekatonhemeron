## 核心主厨：Mortar

在我们的厨房里，`Mortar` 就是那位负责把控全局的主厨。它不仅能处理复杂的对话分支，还能通过“绑钉”系统（`bevy_mortar_bond`）直接插手游戏世界的运行。

通过在 `.mortar` 文件里编写简单的逻辑，你可以决定什么时候播放音效，什么时候触发一段动画，甚至是改变游戏的状态。它就像是预制菜包里的调料包，什么时候加、加多少，全由你这个“厨师”说了算。

看看这语法，是不是比你想象的要简单？

```mortar
node Start {
    text: "你发现了一个装满“预制菜”的箱子。"
    choice: [
        "拿走它" -> TakeIt,
        "无视它" -> IgnoreIt,
    ],
}

node TakeIt {
    run_event(name: "get_item", args: ["pre_made_dish"])
    text: "你感到了某种便利的救赎。"
} -> End

node IgnoreIt {
    text: "你觉得还是亲手装修厨房比较有尊严。"
} -> End
```

## 模块化流水线：Chapter 系统

如果说 Mortar 是调料，那我们的战斗系统就是一套流水线。我把它设计成了 **数据驱动的线性序列执行器**。

每一个战斗环节都被拆成了一个原子单位：**Chapter**（章节）。
- **PlayerInput Chapter**: 玩家选技能、吃药。
- **Dialogue Chapter**: 怪物嘲讽你。
- **BulletHell Chapter**: 各种弹幕糊脸。

通过一个 `RON` 格式的“菜单”（Sequence），你可以像编排播放列表一样组合这些 Chapter。这就像是把一顿大餐拆成了几道预制菜，你想先吃冷盘（对话）还是先吃主食（弹幕），改一行配置就行。

```ron
// 战斗流程配置示例
[
    Chapter(PlayerInput),
    Chapter(Dialogue(node: "boss_insult")),
    Chapter(BulletHell(duration: 5.0, pattern: "pattern_01")),
    Loop(index: 0),
]
```

## 进口食材：ABI 外包系统

当然，有些大厨（Mod 作者）可能觉得预制菜不够劲儿，非要自己手搓一些复杂的硬菜——比如那种需要高性能计算的 3D 弹幕算法，或者是极其复杂的 Boss AI。

这时候，单纯的脚本可能就有点力不从心了。于是我开了一个“后门”：**ABI 外接系统**。

通过定义一套严格的 C 兼容接口（C-ABI），我把 Rust 引擎的核心能力——输入检测、物理运动、日志系统——都暴露了出来。你可以用 **Rust**、**C#** 甚至 **Haxe** 来编写动态链接库（DLL/.so），然后让游戏引擎去加载它们。

### 特别鸣谢：Haxe (类 GML)

特别要提一嘴 **Haxe**。我知道很多 UT/DR 社区的老前辈都是从 GameMaker 时代过来的，习惯了 GML 那种语法。

Haxe 的语法和 GML 非常接近，而且能编译成高性能的 C++ 或者 HashLink。所以，如果你是 GML 老手，用 Haxe 写 Mod 会让你有一种回家的感觉。不用去啃 Rust 的借用检查，也不用忍受 C# 的庞大运行时，Haxe 就是为你准备的“舒适区”。

### 弹幕 VTable

特别是弹幕系统，我设计了一个 `DanmakuVTable`。这意味着你可以用 C# 或 Haxe 写一个拥有完整生命周期（`on_enter`, `on_update`, `on_exit`）的弹幕算法。Rust 引擎负责渲染和碰撞，而你的 DLL 负责计算每一帧的轨迹。性能？那绝对是原生级的。

## Rust 负责烧水，脚本负责加料

这就是我们的哲学：Rust 负责那些吃力不讨好的重活儿——渲染、物理、资源管理。而脚本和配置文件则负责那些有趣的“灵魂”内容。

通过 `bevy_mortar_bond`，我把 Mortar 的逻辑桥接到了 Bevy 的 ECS 体系里。脚本触发一个事件，Rust 这边对应的 System 就会心领神会地执行任务。这种解耦让装修工作变得异常轻松：你不需要重新编译整个项目，只需要换个“预制菜包”，游戏的内容就完全变了。
